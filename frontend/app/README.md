# えんじいろ UI モック（frontend/app）

**PC を主にした 3 カラム構成**の UI モック。React + TypeScript + Vite。
**データは静的ダミーで、backend には接続しない。**

```
┌──────────┬────────────────┬──────────────┐
│ 左サイド │  中央          │ 右サイド     │
│ ホーム   │  タイムライン  │ よみもの     │
│ さがす   │  バブル詳細    │ （準備中）   │
│ おしらせ │                │              │
│ おきにいり│      [バブる] │              │
│ プロフィール│             │              │
│ せってい │                │              │
└──────────┴────────────────┴──────────────┘
```

左サイドを押すと**中央だけ**が差し替わる。`バブる` を押すと右サイドが投稿パネルに
入れ替わり、中央が左へ詰まる（中央はスクロールできたまま）。
同じパネルを返信でも使い回す。

正本の階層は [`../../AGENTS.md`](../../AGENTS.md) →
[`../../docs/specification.md`](../../docs/specification.md) →
[`../../docs/design_doc.md`](../../docs/design_doc.md) →
[`../../DESIGN.md`](../../DESIGN.md) の順。上が常に優先。

## 動かす

```bash
cd frontend/app
npm install
npm run dev      # http://localhost:5173
```

```bash
npm run build    # tsc -b + vite build
npm run lint     # oxlint
```

## 画面の上にある「モック操作」帯

**製品の UI ではない。** 画面の操作だけでは作れない状態を出すための足場で、
実 API に差し替えるときにこの帯ごと外す（`src/components/MockControls.tsx`）。

| つまみ | できること |
|---|---|
| テーマ | OSに従う / ノーマル / ダーク / 園児UI を切り替える |
| AI | AI 推論が停止している状態を作る（NFR-001〜003 の確認用） |
| フィード | ふつう / 読み込み中（skeleton）/ 空 を切り替える |

S3 の下端にも「block になる例」「rewrite_required になる例」というモック用のボタンがある。
入る文言は `src/data/moderationSamples.ts`。フィードには流していない。

## ファイルの置き場所

```
src/
  tokens/      3テーマの CSS 変数と、書体・動き・余白のトークン
    theme.css        ★ 色を書いてよい唯一のファイル
    typography.css   書体階層（.t-bubble-body など）
    motion.css       動きのトークンと5つの keyframes、reduced-motion
    base.css         余白・レイアウト・フォーカス・共通の地ならし
  components/  共通部品（LeftRail / RightRail / ReactionRow / BubbleCard / BubbleBody …）
  screens/     TimelineScreen / BubbleDetailScreen / ComposePanel / PlaceholderScreen
  data/        静的ダミーデータ
    api.ts           ★ サーバとの境界。実 API 差し替え時はここだけ触る
    types.ts         ドメイン型（accountId 相当のフィールドを持たない）
    reactions.ts     ★ 対象別リアクションの唯一の定義
  lib/         mockAiTransform / mockModeration / 相対時刻 / テーマ / あやすの返信規則
```

差し替えるときに触る場所は 2 つだけ：

- **API 接続**：`src/data/api.ts` の各関数の中身を `fetch` にする。画面側は触らない
- **配色の確定**（DESIGN.md §2.2 のノーマルが未確定）：`src/tokens/theme.css` の
  素の `:root` の値。コンポーネントに hex は 1 つも無い

## 確認のしかた

`npm run dev` で開いて、モック操作帯を動かしながら見る。実装時に通した確認は次のとおり。

### 1. 3テーマ × 画面

1440×900 の Chrome で 3 テーマを目視。ダークで臙脂のボタンが地に溶けていないこと
（ダークの主ボタンは `--accent-fill` `#B54254`。臙脂 `#9B3342` は暗い地で 2.54:1 しか出ないため使わない）。

### 2. コントラスト実測

`src/tokens/theme.css` の実値から、実際に使っている 22 組 × 3テーマ = 66 組を計算し、
規約（本文 4.5:1 / 大きい文字と部品 3:1）を割るものが無いことを確認済み。
DESIGN.md §2 に載っている実測値と一致する（ダーク `accent-line` 7.40:1、
ダーク `accent-fill` の輪郭 3.34:1、園児UI `accent-line` 5.43:1）。

もっとも余裕が無いのは園児UI の次の 3 組。**配色を触るときはここから壊れる。**

| 組み合わせ | 比 |
|---|---|
| `mother` `#2E7A50` on `mother-soft` `#E4F3DC` | 4.52:1 |
| `accent-line` `#C22648` on `accent-soft` `#FFE0E6` | 4.65:1 |
| `muted` `#7A675C` on `mother-soft` `#E4F3DC` | 4.63:1 |

#### 規約が無く、判断が要る組み合わせ（独立監査で指摘）

`--hairline` の 1px 枠線と、`--surface` と `--canvas` の差は、DESIGN.md §2 に規約がない。
実測すると WCAG 1.4.11（部品の境界 3:1）を3テーマとも下回る。

| 組み合わせ | ノーマル | ダーク | 園児UI |
|---|---|---|---|
| `hairline` vs `canvas` | 1.26:1 | 1.41:1 | 1.56:1 |
| `hairline` vs `surface` | 1.30:1 | 1.32:1 | 1.64:1 |
| `surface` vs `canvas` | 1.04:1 | 1.07:1 | 1.05:1 |

面と地がほぼ同じ明るさなので、入力欄やタグの輪郭は実質 1px の線だけが頼りになる。
**値を勝手に直していない。** `hairline` は DESIGN.md が役割ごとに決めた色で、
ダークと園児UI の配色は「確定候補（実測済み）」とされている。パレットの変更は
見た目の正本を持つ人間の判断なので、Issue に出して待っている（§2.2 の
「配色を差し替えるときの条件」に6番目を足す提案を含む）。
`prefers-contrast: more` では `hairline` を `muted` へ寄せる退避があるが、既定では効かない。

### 3. 幅ごとの畳み方

| 幅 | 見え方 |
|---|---|
| 1200px 以上 | 3カラム（左 220 / 中央 600 / 右 320）。パネルを開くと右が 440 になる |
| 768〜1199px | 右サイドを畳み、左サイドはアイコンだけの細い列（72px）。パネルは画面に重なる |
| 767px 以下 | 1カラム。左サイドは下部のバー。バブるボタンは右下に固定 |

1440 / 1200 / 1000 / 700 / 375px のいずれでも横スクロールなしを確認済み。

### 4. キーボードだけで ホーム → 詳細 → 返信 → 送信

Tab でバブルカードに到達（フォーカスは `2px solid var(--accent-line)`）→ Enter で詳細 →
Tab であやすボタン → Enter でパネル（開いた直後のフォーカスは本文欄）→ 入力 →
Shift+Tab で送信 → Enter。到達・送信まで確認済み。Escape でパネルが閉じる。

### 5. prefers-reduced-motion: reduce

移動・拡大・跳ね・ぼかしの原資になっているトークン（`--distance-*` / `--scale-modal` /
`--press-scale` / `--pop-scale` / `--blur-*`）を 0 と 1 に潰し、`--ease-bounce` を
`--ease-smooth-out` に差し替える。`opacity` と色の変化は時間そのまま残る（`--duration-fast` は 250ms のまま）。
粒子（`.eg-burst`）は等価物が無いので `display: none`。

### 6. grep での自己点検

```bash
# 色の直書き（tokens/theme.css 以外に hex / rgb / hsl が無いこと）
grep -rnE "#[0-9a-fA-F]{3,8}\b|rgba?\(|hsla?\(" src --include=*.css --include=*.tsx --include=*.ts \
  | grep -v "^src/tokens/theme.css"

# transition: all（コメント以外に無いこと）
grep -rn "transition:\s*all" src

# 絶対時刻の整形（無いこと。相対表示は lib/relativeTime.ts だけ）
grep -rnE "toLocale(Date|Time|)String|Intl\.DateTimeFormat" src

# accountId（コメント以外に無いこと）
grep -rni "accountid" src
```

  FR-AI-TRANS-009 と衝突するため上位文書に従った。**backend の I/F を決めるときに要確認**
- **自分のバブルへの「あやす」を赤ちゃんに限定している**（`lib/soothePersonaRule.ts`）。
  仕様書の制約ではなく、DESIGN.md §0.1-1「同じ画面に自分の両ペルソナを並べない」から導いた

- **意味色（`--success` / `--warning` / `--error`）と `--mother-fill` はどの画面でも未使用。**

## 独立監査（DESIGN.md §9.3）で直したもの

作った本人の自己採点は当てにならないので、別の文脈で §9.3 の監査プロンプトを回した。
指摘のうち、実装側で直せるものは直した。

| 指摘 | 直す前 | 直した内容 | 理由 |
|---|---|---|---|
| コメントと実装の食い違い | `ScreenHeader.css` の先頭コメントが「上 padding を 1.07 倍にする」と書いているのに、実装は上下とも `--space-sm` で同値だった | `--head-padding-top: 14px` / `--head-padding-bottom: 13px` を足して 1.077 倍にした | コメントが主張する効果を実装が出していなかった。12px 基準では 1.05〜1.08 倍の中に整数が無い（12.6〜12.96px）ので、整数で収まる 14 / 13 を採った（DESIGN.md §5.3-1、±2px 以内） |
| トークンを経由しない生の px | `TimelineScreen.css` の帯の罫線が `border-left: 2px` の直書き | `calc(var(--border-width) * 2)` にした | 一点物の装飾でも線の太さはテーマに従うべき。園児UI では 4px になる |
| `rewrite_required` と `block` が読み分けられない | 見出しが両方「このままでは投稿できません」で、アイコンもどちらも盾だった | `block` の見出しを「匿名性を守るため、投稿できません」にし、`rewrite_required` のアイコンをペンにした | 疲れているときに本文の一行だけで読み分けさせない。見出しに理由が入るぶん FR-MOD-033 にも寄る |
| 下部ナビの現在地が色と太さだけ | `.is-current` が色＋`font-weight: 700` のみ | 現在地に印（モバイルは上の横棒、デスクトップは左の縦棒）を足した | 色だけで情報を伝えない（DESIGN.md §2.5）。他の要素は二重化できていたのにここだけ弱かった |
| トークンに無い生の ms | `Toast.tsx` の `VISIBLE_MS = 2600` に説明が無かった | アニメーションの長さではなく表示の保持時間だという理由をコメントにした | motion.css のトークンは遷移時間のスケールで、保持時間はその対象外 |

直していない指摘：

- **`hairline` の境界線が 3:1 を割っている**（上記）。パレットは見た目の正本を持つ人間の判断なので、
  Issue に出して待っている
- **S3 の「バブルはいつでも赤ちゃん」の注記と、その下の `disabled` ボタンが同じことを二度言っている**。
  どちらも DESIGN.md が指定している（§4 Note Box の用例と §0.3）ので、そのまま残した
- **仕様書に無い独自判断が人間承認前に有効になっている**（自分のバブルへのあやすの制限）。
  指摘は正しい。Issue で判断を待っている。実装は `lib/soothePersonaRule.ts` の1か所に集約してあり、
  方針が変われば1か所の変更で済む

## モックであることの限界

- **フロント側のモデレーションと文字数チェックは、保証にはならない。**
  本番では保存時にサーバ側で必ず再検査する（FR-MOD-003/004、NFR-004）。
  `data/api.ts` の検査は「境界で弾く形」を示すためのもの
- 同じく、リアクションの組み合わせ（FR-REACT-007）とあやすの返信ペルソナ（FR-COMMENT-006）も、
  サーバ側で弾くのが本体。フロントは「そもそも出さない」を担保する側
- 再読み込みするとダミーデータは初期状態に戻る（保存先を持たない）

## DESIGN.md との食い違い（改訂案を出す前提で先に実装している）

人間の決定（2026-08-25）で PC 3カラムに切り替えたため、次の3点が正本と食い違っている。

| DESIGN.md | 実装 |
|---|---|
| §5.2「カラムを増やさない（2列にするとバブルを流し読みする対象に変えてしまう）」 | 3カラム。ただし中央のフィードは 600px のまま広げていない |
| §8.1「モバイルファースト・既定は 375px・主要アクションは画面下 1/3」 | PC 既定。バブるボタンは中央の右下 |
| §0.2「1種のリアクションは左寄せ」 | 右寄せ（押しやすい側に寄せる） |

§7.3「MVP で入れる動きは5つだけ」については、パネルの出入りを `modal` 型の使い回しとして扱い、
中央が左へ詰まる動きも同じ duration / easing にして、ひとつの運動として読ませている。

# えんじいろ UI モック（frontend/app）

**PC を主にした 3 カラム構成**の UI モック。React + TypeScript + Vite。
**データは `public/data/*.json` のダミーで、backend には接続しない。**
JSON を書き換えて再読み込みすれば画面が変わる（ビルド不要）。詳しくは
[`public/data/README.md`](public/data/README.md)。

```
┌──────────┬────────────────┬──────────────┐
│ 左サイド │  中央          │ 右サイド     │
│ ホーム   │  タイムライン  │ よみもの     │
│ さがす   │  バブル詳細    │ （準備中）   │
│ おしらせ │                │              │
│ おきにいり│      [バブる] │              │
│ プロフィール│             │              │
│ せってい │                │              │
└──────────┴────────────────┴──────────────┘
```

左サイドを押すと**中央だけ**が差し替わる。`バブる` を押すと右サイドが投稿パネルに
入れ替わり、中央が左へ詰まる（中央はスクロールできたまま）。
同じパネルを返信でも使い回す。

**見た目の方向性は「よふけの バブル」**（UI刷新 2026-08-26）。地・光・輪の3層を敷いた場に、
本文の入った吹き出しが浮かんでいる、という一枚の絵として画面を組む。
角丸の長方形を縦に並べる形をやめたのは、それが一番強く「よくある SNS」に見えていたため。
詳しくは下の「UI刷新（2026-08-26）」。

正本の階層は [`../../AGENTS.md`](../../AGENTS.md) →
[`../../docs/specification.md`](../../docs/specification.md) →
[`../../docs/design_doc.md`](../../docs/design_doc.md) →
[`../../DESIGN.md`](../../DESIGN.md) の順。上が常に優先。

## 動かす

```bash
cd frontend/app
npm install
npm run dev      # http://localhost:5173
```

```bash
npm run build    # tsc -b + vite build
npm run lint     # oxlint
```

## 画面の上にある「モック操作」帯

**製品の UI ではない。** 画面の操作だけでは作れない状態を出すための足場で、
実 API に差し替えるときにこの帯ごと外す（`src/components/MockControls.tsx`）。

| つまみ | できること |
|---|---|
| テーマ | OSに従う / ノーマル / ダーク / 園児UI を切り替える |
| AI | AI 推論が停止している状態を作る（NFR-001〜003 の確認用） |
| フィード | ふつう / 読み込み中（skeleton）/ 空 を切り替える |

S3 の下端にも「block になる例」「rewrite_required になる例」というモック用のボタンがある。
入る文言は `src/data/moderationSamples.ts`。フィードには流していない。

```

    typography.css   書体階層（.t-bubble-body など）
    motion.css       動きのトークンと5つの keyframes、reduced-motion
    base.css         余白・レイアウト・フォーカス・共通の地ならし
  components/  共通部品（LeftRail / RightRail / ReactionRow / BubbleCard / BubbleBody …）
    Illustration.tsx ★ イラストの出し口。テーマごとに SVG ファイルを選び替える
    BrandMark.tsx    ブランドの印（しっぽ付きの吹き出しに「…」）
  screens/     TimelineScreen / BubbleDetailScreen / ComposePanel /
               MyProfileScreen / PublicProfileScreen / FavoritesScreen /
               SignUpScreen / LoginScreen / IntroScreen / PlaceholderScreen
  data/        データ層
    api.ts           ★ サーバとの境界。実 API 差し替え時はここだけ触る
    mockSource.ts    public/data/*.json を読みに行くだけの層。実 API 差し替え時に消える
    types.ts         ドメイン型（accountId 相当のフィールドを持たない）
    reactions.ts     ★ 対象別リアクションの唯一の定義
  lib/         mockAiTransform / mockAiEvaluate / mockModeration / 相対時刻 /
               生年月日 / テーマ / あやすの返信規則
    useResolvedTheme.ts ★ いま実際に効いているテーマ（normal/dark/kid）を返す。
                          <img> の SVG には CSS 変数が継承されないので、
                          「変数を渡す」のではなく「ファイルを選ぶ」ために要る

public/data/   ★ ダミーデータの実体（JSON）。書き換えると画面が変わる
public/images/ ★ イラスト（frontend/images/*.svg のコピー）。テーマごとに3ファイル
```

差し替えるときに触る場所は 2 つだけ：

- **API 接続**：`src/data/api.ts` の各関数の中身を実 API への `fetch` にする。
  `src/data/mockSource.ts` と `public/data/` はそのとき消える。画面側は触らない
- **配色の確定**（DESIGN.md §2.2 のノーマルが未確定）：`src/tokens/theme.css` の
  素の `:root` の値。コンポーネントに hex は 1 つも無い

## UI刷新（2026-08-26）

### 何を変えたか

| ところ | 前 | 後 |
|---|---|---|
| 画面の地 | `--canvas` の一色 | 地 → 光（`--aura-*` の放射グラデ）→ 輪（細い円4つ）→ 中身 の4層。**動かさない**（`position: fixed`） |
| 列の仕切り | 中央の列の左右に 1px の縦線 | 縦線を廃止。左右を「島」（面）にして、中央を余白で切る |
| バブルカード | 角丸の長方形。上にニックネーム、下に本文 | **しっぽ付きの吹き出し**。中に本文、しっぽの先に書いた人、その下にリアクション |
| タイムラインの先頭 | 「ホーム」の見出しだけ | 口上（呼びかけ1行）を主役として置く。送れば流れて消える |
| Intro | 説明カード1枚 | 表紙（名乗り・ひとこと・イラスト）＋説明カードの2面 |
| 投稿パネルの入力欄 | 角丸の箱 | 吹き出しの形。空のときだけ中にイラストが出て、書き始めると消える |
| 文字数カウンタ | 数字だけ | ふくらんでいく輪 ＋ 数字（DESIGN.md §4 Meter の「バーだけで伝えない」に合わせる） |
| リアクション | 角丸（`--radius-control`） | 丸（`--rounded-pill`）。確定操作のボタンと形で分ける |
| 完了のしらせ・AI 変換案 | 角丸の箱 | どちらも吹き出し。画面から出る「ことば」を同じ形にそろえる |

追加したトークン（`tokens/theme.css`、どれも既存の役割名から `color-mix` で作る。生の hex は増やしていない）：

- `--aura-warm` / `--aura-cool` … 光の層の色
- `--field-ring` / `--field-ring-width` … 輪の色と太さ
- `--radius-balloon` / `--balloon-tail-size` / `--balloon-tail-inset` … 吹き出しの形
- `--radius-reply` … 返事（あやす）の形。吹き出しと左右を反転させる

**3テーマの差は色だけではない。** 光の量・輪の太さ・吹き出しの角の形をテーマごとに変えている
（園児UI は輪が 2 倍太く、吹き出しが不定形）。骨格（余白・書体・動き・コンポーネントの構造）は
DESIGN.md §1.2 のとおり共通のまま。

### イラストの使い分け

素材は `frontend/images/` の 3 種 × 3 テーマ ＝ 9 ファイル。**全部使っている**が、
画面ごとに役割を分けていて、同じ絵を全画面に出さない。イラストを置かない画面のほうが多い。

| ファイル | どこで | なぜ |
|---|---|---|
| `soft-bubble-orbit-*.svg` | **Intro の表紙（主役）** | 「めぐるバブル」。吐き出したものが受け止められて戻ってくる、というこのサービスの主張がそのまま絵になっている。表紙は説明ではなく世界観を出す場所なので、いちばん強い絵をここに置いた |
| `soft-bubble-haven-*.svg` | **空状態の主役**（タイムラインが空 / おきにいりが空） | 「ひとやすみのバブル」。静かで、何も無いことを責めない絵柄。空状態は「まだ無い」を伝える場所なので、余白の中に置ける絵が要る |
| `soft-bubble-drops-*.svg` | **投稿パネルの入力欄の中**（本文が空のときだけ） | 「しずくのバブル」。上に落ちるしずくが「吐き出す」に直接つながる。書き始めると `opacity` だけで消える（要素は残すので高さが跳ねない） |

置かなかったところ：タイムライン本体、バブル詳細、あやす詳細、プロフィール、ログイン・登録。
タイムラインは**吹き出しが並んでいること自体**が絵なので、そこへイラストを足すと主役が2つになる。
詳細とプロフィールは読むための画面で、絵を置く場所は本文の面積を削る。

**`<img>` で読み込んだ SVG に、アプリ側の CSS 変数は継承されない。**
素材側は `var(--illustration-fill, #F4C7B8)` のようにフォールバック色を持っていて、
外部読み込みではそのフォールバックが効く。だから色を渡すのではなく
`lib/useResolvedTheme.ts` で**ファイルを選び替えている**（`components/Illustration.tsx`）。
判定材料は `<html data-theme>` と `prefers-color-scheme` の2つで、
`tokens/theme.css` の実装契約（DESIGN.md §8.3）と同じ順序。

イラストはすべて装飾なので `alt=""` ＋ `aria-hidden="true"`、`pointer-events: none`。
意味は隣の文字（口上・空状態のコピー・placeholder）が持つ。

### 増やした依存

**無し。** 背景の層・吹き出しのしっぽ・カウンタの輪・出入りの動きは、すべて CSS と既存トークンで作っている。
shadcn/ui・Tailwind・Motion のいずれも入れていない。

## 5つの指摘への対応（2026-08-27）

人間から直接受けた指摘5件。

### 1. 「バブる」が主役に見えない → 大きさ・登場・誘い・反応の4つを重ねた

> 一番押してほしいボタンはバブルなので、そこに対してアクションやアニメーションを追加してください。

| 何を | どうした |
|---|---|
| 大きさ | `--fab-height` を新設（56px）。ほかのボタンは 48px のまま。**色と位置だけでなく大きさでも主役**にする |
| 登場 | 画面に着いたとき、下から一度だけ浮かび上がる（`eg-fab-in`。`modal` 型の使い回し） |
| 誘い | そのあと輪が2回ひろがって**止まる**（`eg-ring-out` の使い回し）。繰り返さない |
| 反応 | カーソル／フォーカスで小さなバブルが3つ立ちのぼる（`eg-fab-drift`）。押すと `--press-scale-strong` で縮む |

- 型は `tokens/motion.css` に `bubble-call` として1か所にまとめた。`DESIGN.md` §7.3 の表も
  「5つ」→「6つ」に直してある
- **常時は動かさない**（§7.2）。誘いが終わったあと、動いているアニメーションが 0 件であることを
  3テーマ × 4幅で実測した
- **キーボードでも同じものが見える**（`:focus-visible`）。マウスを持っている人にだけ反応する形にしない
- reduced motion では輪と立ちのぼりを `display: none` にする。移動の原資が 0 に潰れると、
  その場で点滅するだけの意味の無い動きになるため。消しても失われる情報は無い

### 2. 「バブる」が最下部にあり、下までスクロールしないと見えない

原因はボタンの側ではなく**外側の骨組み**にあった。

- 上にモックの操作帯（`.eg-mock`、78〜206px）が積まれている。中央の列は `100vh` で作られていたので、
  **列の下端＝ viewport の下端 ＋ 操作帯の高さ**。そこに貼りついたボタンは最初から画面の外に居た
  （1440×800 で `top: 807px`）
- 直し方：`.eg-app--shell` を縦に積む箱にして高さを `100dvh` に固定し、余りを `.eg-layout` に配る。
  さらに `grid-template-rows: minmax(0, 1fr)` で行の高さを**決まった値**にした。
  ここが `auto`（＝決まっていない）だと、中の `.eg-center` が書いている `100%` が `auto` に化けて効かない
- 併せて `.eg-rail` と `.eg-compose` の `100vh` を `100%` にした。viewport から取ると、
  上に積まれたぶんだけ下へはみ出すため
- **ボタンを中央の列の外へ出した**（人間の決定 2026-08-27「常に表示されている状態を優先」）。
  列の中に居るということは「読みものの流れの一部」ということでもあり、キーボードだけで
  操作する人はカードを全部通り過ぎてからしか届かなかった。
  DOM 上は左サイドの直後に置き、見た目の位置は grid の列指定（2列目・下端・右寄せ）で決める。
  製品側のタブ順は **ホーム → さがす → おしらせ → おきにいり → プロフィール → せってい →
  バブる → あたらしくする → 本文 → 書いた人 → リアクション**。
  見た目の位置・逃げ幅（右 28px / 下 24px）・フィード幅 600px は前と1px も変えていない
- 列の末尾には中身の無い `.eg-fab-slot` だけを残した。ボタンぶんの高さを確保するためのもので、
  これが無いと いちばん下まで送りきったとき最後のカードがボタンの下に隠れる
- 結果：PC ではページ自体が動かなくなり（`pageScroll: 0`）、左右の列も「バブる」も常に見えている。
  767px 未満はこれまでどおりページを送る（ボタンは `fixed`）
- **入口の画面（説明・登録・ログイン）にはこの固定を効かせない**（`--shell` を付けていない）。
  あちらは1枚の紙が縦に伸びる作りで、高さを固定すると背の低い画面で下が読めなくなる

### 3. 「もどる」がホームに着地する → 通ってきた道を1本の配列にした

> おきにいり → アカウントページ → バブル のあと、もどるとホームへ行ってしまう。

- 原因：`view`（左サイドの選択）／`detailStack`（詳細の積み重ね）／`publicBackTo`（S6 の戻り先）の
  **3つを別々に持っていた**。プロフィールからバブルを開くとき、途中で `view` を `timeline` に
  書き換えていたので、来た道がどこにも残らなかった
- 直し方：`Location`（`view` / `public` / `bubble` / `soothe`）の配列 1本にまとめた。
  中央に出せるものは、左サイドの画面も公開プロフィールも詳細も、等しく「場所」として1段積む。
  「もどる」は種類を問わず1段外すだけで、戻り先を覚える変数は要らなくなった
- 底は常にホーム。**左サイドを押したときだけ**積み上げを捨てて底から始め直す
- 着いた先は毎回引き直す（進むときも戻るときも同じ `enter()` を通す）。潜っているあいだに
  増えたリアクションやあやすが、戻った瞬間に消えたように見えないため
- 実測：`おきにいり → 公開プロフィール → バブル → もどる → 公開プロフィール → もどる → おきにいり`。
  `ホーム → バブル → あやす → もどる → バブル → もどる → ホーム` も同じ

### 4. 「よんだ／まだ」を廃止した

> 実装依頼をしていないかと思います。バックエンド側に送る API も無いだろうし。

- 仕様書・設計書のどちらにも「既読」は**1語も無い**（`grep` で確認）。送り先の API も無い
- 画面だけが覚えている「よんだ」は、別の端末で開けば嘘になる。本人にしか意味が無い情報のために、
  カード1枚あたり1行ぶんの高さを使っていた
- 型（`Bubble.read`）・モックの種（`BubbleSeed.read`・`bubbles.json`）・`markRead()` ごと落とした。
  画面から消すだけにすると、次に触る人が「送り先があるはず」と思い込む
- 詰めたぶん：2段目（書いた人の行）から右端の印が消え、3段目（リアクション行）との間を
  `--space-xs` → `--space-xxs` に近づけた。1枚が1つの塊に見える
- **失われた情報は無い。** 誰が・いつ・どれだけあやされたかは、吹き出しの中と2段目にそのまま残る

### 5. 登録画面に生年月日の欄を追加した

- S8 本人専用プロフィールには**前から生年月日が出ていた**のに、入れる場所がどこにも無かった
- パスワードとニックネームのあいだに置いた。`type="date"`、`min` は 1900-01-01、`max` はきょう
- **これはアカウントの情報で、ペルソナの情報ではない。** 公開プロフィール（S6）の型にこの項目は無く、
  AI へ渡す入力にも入らない（FR-PRIV-003/004）。そのことを入力欄のすぐ下に書いてある
  （「自分のプロフィールにだけ 出ます。ほかの人からは 見えません」）。
  ここで黙って受け取ると、なぜ要るのか分からないまま個人の情報を書かせることになる
- 年齢で入会を断る判定は**入れていない**。年齢制限は仕様書に無く、決めるのは人間（Issue #7 と同じ扱い）
- 併せて `tokens/theme.css` に `color-scheme` を足した。これが無いと、ブラウザが自前で描く
  カレンダーの印がダークで黒いまま出て地に沈む。スクロールバーと選択文字の地も同時に揃う

### 1. 3テーマ × 画面

1440×900 の Chrome で 3 テーマを目視。ダークで臙脂のボタンが地に溶けていないこと

### 2. コントラスト実測

配色を変えたので測り直した。**手写しではなく、ブラウザが実際に描画している値**
（`getComputedStyle` で `var(--*)` を解決したもの。`color-mix` も解決される）を取り、
3テーマ × 19 組を計算している。

| テーマ | 条件を割った組 | 主役の序列（赤ちゃん vs お母さん） | 面の段 |
|---|---|---|---|
| ノーマル | 0 | 6.77 vs 5.54 → **+1.23** | OK |
| ダーク（紺） | 0 | 7.48 vs 6.33 → **+1.15** | OK |
| 園児UI | 0 | 5.43 vs 4.96 → **+0.48** | OK |

**ダークの逆転（前は −1.68）が解消した。** 園児UI の +0.48 は薄いままで、
可読性の下限があるため詰められない（上の「実装していないもの」）。

もっとも余裕が無いのは園児UI の次の 3 組。**配色を触るときはここから壊れる。**

| `accent-line` `#C22648` on `accent-soft` `#FFE0E6` | 4.65:1 |
| `muted` `#7A675C` on `mother-soft` `#E4F3DC` | 4.63:1 |

#### 規約が無く、判断が要る組み合わせ（独立監査で指摘）

`--hairline` の 1px 枠線と、`--surface` と `--canvas` の差は、DESIGN.md §2 に規約がない。
実測すると WCAG 1.4.11（部品の境界 3:1）を3テーマとも下回る。

| 組み合わせ | ノーマル | ダーク | 園児UI |
|---|---|---|---|
| `hairline` vs `canvas` | 1.26:1 | 1.41:1 | 1.56:1 |
| `hairline` vs `surface` | 1.30:1 | 1.32:1 | 1.64:1 |
| `surface` vs `canvas` | 1.04:1 | 1.07:1 | 1.05:1 |

面と地がほぼ同じ明るさなので、入力欄やタグの輪郭は実質 1px の線だけが頼りになる。
**値を勝手に直していない。** `hairline` は DESIGN.md が役割ごとに決めた色で、
ダークと園児UI の配色は「確定候補（実測済み）」とされている。パレットの変更は
見た目の正本を持つ人間の判断なので、Issue に出して待っている（§2.2 の
「配色を差し替えるときの条件」に6番目を足す提案を含む）。
`prefers-contrast: more` では `hairline` を `muted` へ寄せる退避があるが、既定では効かない。

## 独立監査（DESIGN.md §9.3）で直したもの

作った本人の自己採点は当てにならないので、別の文脈で §9.3 の監査プロンプトを回した。
指摘のうち、実装側で直せるものは直した。

| 指摘 | 直す前 | 直した内容 | 理由 |
|---|---|---|---|
| コメントと実装の食い違い | `ScreenHeader.css` の先頭コメントが「上 padding を 1.07 倍にする」と書いているのに、実装は上下とも `--space-sm` で同値だった | `--head-padding-top: 14px` / `--head-padding-bottom: 13px` を足して 1.077 倍にした | コメントが主張する効果を実装が出していなかった。12px 基準では 1.05〜1.08 倍の中に整数が無い（12.6〜12.96px）ので、整数で収まる 14 / 13 を採った（DESIGN.md §5.3-1、±2px 以内） |
| トークンを経由しない生の px | `TimelineScreen.css` の帯の罫線が `border-left: 2px` の直書き | `calc(var(--border-width) * 2)` にした | 一点物の装飾でも線の太さはテーマに従うべき。園児UI では 4px になる |

## モックであることの限界

- **フロント側のモデレーションと文字数チェックは、保証にはならない。**
  本番では保存時にサーバ側で必ず再検査する（FR-MOD-003/004、NFR-004）。

  サーバ側で弾くのが本体。フロントは「そもそも出さない」を担保する側
- 再読み込みするとダミーデータは初期状態に戻る（保存先を持たない）

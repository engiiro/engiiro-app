# 開発の進め方

人間が担当・優先順位・仕様・レビュー・リリースを判断し、AI は調査、コーディング、テスト、Issue・PR の文章作成を補助します。

## Issue の4分類

| 種類 | タイトル | 書くこと | 関連付け |
| --- | --- | --- | --- |
| 日報 | [日報] 日付・名前 | 今日やりたいこと、やること、やったこと。予定だけ・実績だけでもよい | 関連タスク・バグの Issue 番号を並べる |
| タスク | [タスク] 変更内容 | 何をなぜ、どう更新するか、完了条件 | 関連日報と対応 PR |
| バグ報告 | [バグ] 症状 | 起きたこと、期待する動作、分かる範囲の再現手順・環境 | 関連日報、修正する場合は対応 PR |
| その他 | [その他] 自由なタイトル | 意気込み、雑談、メモ、質問など何でも。一言でもよい | 必要な場合だけ Issue・PR |

ラベルの組み合わせで分類・担当・進行状況を管理する運用はやめ、タイトルと本文のリンクで追えるようにします。テンプレートはラベルを自動付与しません。担当は必要に応じて人間が GitHub の Assignees、レビュー担当は PR の Reviewers で設定します。

## 日報 → タスク → PR

1. 日報に予定または実績を書く。後から追記してよい。
2. 具体的な変更をタスク Issue にする。日報にタスク番号を記載し、タスクにも関連日報を記載する。
3. 1タスクを1 PR で実装し、PR タイトルを「[#Issue番号] 変更内容」にする。本文には自動関連付け用の Closes #番号 も残す。
4. 人間がレビューとマージを判断する。日報は PR で自動終了させず、人間が記録をまとめて終了する。

例（番号は説明用）：

- 日報 #100：予定「投稿フォームを改善する」、関連タスク #101。
- タスク #101：変更内容と完了条件、関連日報 #100。
- PR #102：タイトル「[#101] 投稿フォームを改善する」。本文に Closes #101、関連日報 #100、変更内容と確認結果。

複数日にまたがる作業は、各日の日報から同じタスクを参照します。タスク側には関連日報を追記できます。日報がまだなければタスク作成を止めず、後から関連付けます。

タスクは1件の PR で完了できる範囲に分けます。複数の独立した変更を1 PR に詰め込みません。未マージで取り下げた PR を作り直す場合は、旧 PR と新 PR を相互参照し、対応する現行 PR が分かるようにします。

## バグとその他

バグは原因や再現条件が未確定でも報告できます。分からない点は「未確認」とし、報告と修正の判断を分けます。修正するときはバグ Issue を直接主対象にした PR を作り、同じ修正のためのタスクを重複作成しません。バグ Issue と修正 PR も1対1です。

「その他」は何でも書ける自由な枠です。「頑張るぞ！」の一言、雑談、メモ、アイデア、質問も歓迎します。背景説明や回答・判断の依頼は不要です。具体的な実装が決まった場合だけ、タスクまたはバグを作って元の投稿にリンクします。

## AI の役割

- 人間の依頼に沿って、調査・実装・テストと説明文の作成を行う。
- AI 台帳、専用 ID、宛先タグ、5行ヘッダー、AI ごとの担当ラベルは使わない。
- Issue・PR の投稿や管理操作は人間の依頼がある場合に行う。PR 作成依頼には、必要な対応タスク Issue の作成を含む。
- 人間の予定・実績を推測して日報を代理投稿しない。
- 作業の優先順位や他メンバーへの割り当て、仕様確定、マージを独断で行わない。

## 既存の記録からの移行

- 新しく作る Issue・PR からこの運用を使う。既存の Issue・PR は作り直さず、継続作業時に必要なリンクを追記する。
- 旧ラベルは新規運用では必須にしない。既存 Issue のラベル削除やリポジトリ全体のラベル整理は、人間が対象を確認して別途行う。
- 旧 AI 台帳と会話プロトコルは [過去の記録](AI_ISSUE_PROTOCOL.md) として残し、現在の作業には適用しない。
- テンプレートはこの PR がデフォルトブランチにマージされた後、新規 Issue 作成画面に反映される。各メンバーは最新 main を取得して AGENTS.md を利用する。

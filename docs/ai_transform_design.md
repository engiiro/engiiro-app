# AI文章変換：Gemini生成 + ルールベースフォールバック 設計書

## 1. 位置づけ

`docs/design_doc.md` 7章 `POST /api/ai/transform`、9章「モデレーション」の実装詳細。
本書は`ai/`配下の変換ロジック（Issue #15の後継）の設計を定める。

正本の優先順位は`docs/design_doc.md` > 本書 > `ai/`配下のコード。矛盾が見つかった場合は
`docs/design_doc.md`を疑い、本書側を直す。

### 1.1 この機能が解決すること

利用者が書いた素の文章を、赤ちゃん・園児語（`style: "baby"`）またはお母さん・ママ語
（`style: "mother"`）へ言い換える。変換方式は2段構えにする。

1. **一次経路**：Gemini API（`gemini-3.5-flash-lite`）によるプロンプトチューニング変換。
   文脈を理解した自然な言い換えができる。
2. **フォールバック経路**：Gemini APIが遅延・エラー・レート制限に達したときに、
   外部通信なしで動くルールベース変換に切り替える。

サーバー運用時にGemini APIへのリクエストが集中すると、応答が間に合わなくなったり
レート制限に達したりする可能性がある（人間監督の懸念）。フォールバック経路は
「Gemini APIが完全に止まっている日でも、変換機能自体は止めない」ことを目的とする。
`ai/moderation_rules.py`（投稿可否のモデレーション）が既に持っている「通信しない判定は
生成APIの状態に左右されない」という設計思想を、変換（生成）側にも広げたものである。

### 1.2 この機能が解決しないこと

- 投稿の可否判定（モデレーション）そのもの。既存の`ai/moderation_rules.py`の
  `check_rules()`が担当し、本書では変更しない。
- 文体の点数化・学習データに基づく分類（「本当に赤ちゃん語になっているか」の判定）。
  これは別Issue（`naive-bayes-sample`のようなラベル付き学習データに基づく方式）で
  扱う想定であり、本書のフォールバック生成は「規則に基づいて機械的に言い換える」
  ことだけを行う。

## 2. API契約

`docs/design_doc.md` 7章の確定仕様（2026-08-27、`action`は`allow`/`block`の2値に統一。
9.2章 FR-MOD-023 との矛盾を解消した）にそのまま従う。

```json
// POST /api/ai/transform
// Request
{ "body": "string", "style": "baby | mother" }

// Response
{
  "action": "allow | block",
  "transformedText": "string | null",
  "reasonCodes": ["string"]
}
```

`ai/app.py`の`/transform`エンドポイントを、design_doc.mdのバックエンド契約と同じ形へ
変更する（現状は`{ transformedText: string }`のみを返しており、`action`と
`reasonCodes`が無い。4章で詳細を述べる）。

`ai/`側のHTTPサービスは、内部実装（Gemini or フォールバックのどちらで変換したか）を
`reasonCodes`や応答に一切含めない。利用者にもバックエンドにも、どちらの経路が
使われたかは見えない（FR-AI-TRANS-009）。ログにのみ記録する。

## 3. 全体フロー

```
transform(body, style)
  │
  ├─ 1. 事前モデレーション（check_rules）
  │     block → { action: "block", transformedText: null, reasonCodes }で終了
  │
  ├─ 2. NGワード置換（マサカリ寄りの語だけを穏当化。5章）
  │
  ├─ 3. Gemini APIで変換を試みる（タイムアウト付き）
  │     成功 → 4へ
  │     失敗・タイムアウト・レート制限 → フォールバック生成（6章）へ
  │
  ├─ 4. 事後モデレーション（変換後の文章に対して check_rules）
  │     block → { action: "block", transformedText: null, reasonCodes }で終了
  │
  └─ 5. { action: "allow", transformedText, reasonCodes: [] }
```

事前モデレーションでblockになった文章は、Gemini・フォールバックのどちらにも
渡さない（個人情報を外部APIへ送らないため。`ai/transform_api.py`が既に採用している
方針と同じ）。

## 4. 一次経路：Gemini API

既存の`ai/transform_api.py`（Issue #15、main反映済み）をそのまま流用する。
新規に書き直さない。

- モデル：`gemini-3.5-flash-lite`（人間監督の指定。`gemma-4-31b-it`では知能が
  不足すると判断され変更された経緯がIssue #15にある）
- `transform_text(mode, text, client=None) -> str`を呼び出す。判定は行わず、
  変換だけを行う関数のため、事前モデレーションは3章のとおり`transform()`側で
  別途行う。
- タイムアウト：環境変数`AI_TRANSFORM_TIMEOUT_SECONDS`（既定4.0秒）。
  Gemini SDK（`google-genai`）の`HttpOptions(timeout=...)`をミリ秒で渡す。
  HTTP経路全体を長時間占有しないための保守的な値であり、実測してから
  調整する前提（Issue #47 P0-4と同じ考え方）。
- リトライ：しない。1回で失敗またはタイムアウトしたら、即座にフォールバックへ
  切り替える。Issue #47 P0-4が指摘するとおり、公開HTTPリクエストでリトライを
  重ねるとworkerを長時間占有するため。
- 例外的に補足する失敗：`RuntimeError`（APIキー未設定、レート制限、認証エラー、
  タイムアウト、空応答）、`TimeoutError`。これら以外の予期しない例外は握りつぶさず
  そのまま送出する（バグを隠さないため）。

## 5. NGワード置換（NG語の端処理）

投稿可否のモデレーション（`block`/`allow`）とは別レイヤーの処理。目的が違う。

| | 対象 | 挙動 |
|---|---|---|
| モデレーション（`check_rules`、既存） | 個人情報・自傷他害・露骨なNG語 | 問答無用で`block`。置き換えない |
| NGワード置換（本章、新規） | マサカリ寄りだが`block`ほど重篤ではない語（既存の`NG_WORDS_REWRITE`：「無能」「役立たず」等） | 変換前に穏当な言葉へ機械的に置き換えてから、通常の赤ちゃん語/お母さん語変換にかける |

`block`にする語は本書では一切触らない。`ai/moderation_rules.py`の`NG_WORDS_BLOCK`・
`SELF_HARM_WORDS`はそのまま維持し、3章の事前モデレーションでblockする。

置換辞書は`ai/dictionaries/harsh_word_softeners.json`に置く。カテゴリ辞書とは
違い1対1の対応なので、`{語: 置換後の語}`のフラットな形で書く。例：

```json
{ "無能": "まだ慣れていない", "役立たず": "これからのびしろがある" }
```

置換は形態素解析前の文字列置換として行う（辞書のキーは短い日本語の語であり、
複合語判定を必要としないため）。置換後の文章がそのままGemini／フォールバックへ渡る。

## 6. フォールバック経路：ルールベース生成

### 6.1 発動条件

- Gemini API呼び出しが`AI_TRANSFORM_TIMEOUT_SECONDS`以内に完了しない
- Gemini APIが例外を送出する（レート制限・認証エラー・空応答等）
- `GOOGLE_API_KEY`が設定されていない（開発環境やAPIキー未設定時にも変換機能自体は
  動かしたいため）

### 6.2 処理パイプライン

```
fallback_transform(body, style)
  1. 形態素解析でトークン化（fugashi）
  2. 辞書の最長一致で単語・複合語を置換（6.4章）
  3. 文末表現を書き換える（6.5〜6.6章）
  4. 一人称を書き換える（baby のみ）
  5. 事後モデレーションへ渡す（3章の4に合流）
```

### 6.3 形態素解析と複合語の扱い

`fugashi[unidic-lite]`を使う（`naive-bayes-sample`と同じ構成。追加インストールが
`pip install fugashi[unidic-lite]`だけで完結し、MeCab辞書を別途セットアップしなくて良い）。

「自動車」のような複合語は、辞書（unidic-lite）の分割単位によっては
「自動」+「車」のように2形態素へ分かれることがある。人間監督の懸念どおり、
形態素単位でそのまま辞書引きすると「自動車」が拾えない。

対策として、**形態素解析の結果を使うのは「文の構造把握」までとし、辞書引きは
「原文の文字列」に対して行う**方式を採る。理由：

- 正規表現や形態素境界だけで「どこまでが1つの複合語か」を判定するのは、
  日本語の分かち書きの曖昧さにより一般には解けない（「自動車」「自動ドア」
  「自動」だけでも別々の語になり得る）。
- 一方、辞書のキー自体（例：「自動車」「セダン」「消防車」）は既知の文字列なので、
  **原文に対して辞書キーを長い順に走査し、最長一致した部分文字列を置換する**
  （`ai/src/fallback/dictionary_match.py`の`replace_longest_match()`）だけで、
  形態素分割の揺れに影響されず複合語を1語として扱える。

```python
# 例：辞書に "自動車" と "動車輪"（架空語）が両方あっても、
# 「自動車」を先に長さ順で試すので正しく「自動車」がマッチする。
replace_longest_match("自動車を運転する", {"自動車": "ブーブー", "運転する": "うんてんする"})
# => "ブーブーをうんてんする"
```

形態素解析（fugashi）は、この後の「文末表現の判定」（6.5章：文末が助動詞
「です」「ます」で終わっているか、活用形は何か）と「未知語をひらがなに開く処理」
（6.6章）にだけ使う。辞書マッチには使わない。

### 6.4 辞書設計

`ai/dictionaries/`配下にJSONファイルとして置く（2026-08-27、Pythonの辞書
リテラルから移行した）。理由：カテゴリごとに数百語規模まで語彙を増やしていく
運用（7章）を前提にすると、Pythonリテラルはカンマの付け忘れ等で構文エラーを
起こしやすく、差分レビューも辛くなる。JSONなら人間・AIによる機械的な追記が
しやすく、非エンジニアメンバーにも編集しやすい。JSON自体にコメント構文が
無いため、`_comment`キーに辞書の説明を書く（読み込み時に`_`で始まるキーは
対象から除く。`ai/src/fallback/dictionary_loader.py`）。

2種類に分ける。どちらも「大人の言葉→赤ちゃん語の候補の配列」という
`{語: [候補, ...]}`の形で書く（2026-08-27、実際の育児語彙を反映する中で
「ママ→まんま／ま／まー／まま」のように1つの大人の言葉に複数の赤ちゃん語
バリエーションがある例が多く出たため、この形に統一した）。人間が読みやすい
よう、トップレベルをサブカテゴリでグルーピングした2階層にしている
（`{サブカテゴリ: {語: [候補, ...]}}`）。実行時は
`dictionary_loader.load_variant_dictionary()`がこれをフラット化し、
候補が複数あれば単語自体の文字数から機械的に1つを選んで
（同じ単語には常に同じ変換結果を返す）、`replace_longest_match()`に渡す
`{語: 赤ちゃん語}`の辞書を作る。

**(a) 日常語彙辞書**（`ai/dictionaries/baby_daily_words.json`）：家族の呼称・
動物・食べ物・乗り物・体の部位・生活動作・排泄・場所・遊びをカバーする、
実際の育児語彙に基づく辞書（人間監督から実例のリストを受け取り反映した）。
車は「セダン等の一般的な車」（→「ぶーぶー」）と「救急車・パトカー・消防車の
ような緊急車両」（→「ぴーぽーぴーぽー」）を別カテゴリに分けている
（人間監督の指示）。

```json
{
  "家族": { "ママ": ["まんま", "ま", "まー", "まま"], "パパ": ["ぱっぱ", "..."] },
  "動物": { "犬": ["わんわん"], "猫": ["にゃんにゃん", "にゃーにゃー", "にゃ"] },
  "乗り物・身につけるもの": {
    "セダン": ["ぶーぶー"],
    "救急車": ["ぴーぽーぴーぽー"], "パトカー": ["ぴーぽーぴーぽー"]
  }
}
```

**(b) エンジニア用語辞書**（`ai/dictionaries/baby_engineer_words.json`）：
人間監督の指定どおり、エンジニアが日常的に使う語を重点的にカバーする。
「お約束」のような1語1言い換えではなく、**同じ意味グループの類義語をまとめて
1つの赤ちゃん語へ寄せるサブカテゴリ化**にしている（人間監督の指示：1000語
規模にするなら1対1ではなく多対1が現実的）。開発フローの各工程（レビュー・
マージ・デプロイ等）は互いに類義語ではないため、工程ごとに別のサブカテゴリに
分けている。

```json
{
  "トラブル": {
    "バグ": ["ばぐばぐ"], "エラー": ["ばぐばぐ"], "障害": ["ばぐばぐ"]
  },
  "開発フロー": { "マージ": ["がっちゃんこ"], "統合": ["がっちゃんこ"] }
}
```

2026-08-27、Web検索で実在が確認できた語彙をサブカテゴリ単位で拡充した
（`baby_daily_words.json`は10サブカテゴリ計237語、`baby_engineer_words.json`は
9サブカテゴリ計117語）。「食べ物・飲み物」（134語）や「開発フロー」（29語）の
ように実在するメニュー名・IT用語が多いカテゴリは大きく伸びる一方、「家族」
（6語）のように音由来の幼児語自体が本質的に少ないカテゴリは無理に増やして
いない。今後も7章「辞書の育て方」に沿って育てていく前提。未知語（辞書に無い
語）は無理に変換せず、6.6章の一般規則（語尾変換等）だけを適用する。

**具体と抽象（2026-08-27追加）**：「馬」の類義語（馬匹・牡馬・牝馬・駿馬・
汗血馬・農耕馬・乗用馬等）や、車の下位にあるボディタイプ（ミニバン・SUV・
クーペ等）のように、**あるカテゴリに属する具体的な種類・品種・呼び方は、
すべて同じ上位カテゴリの赤ちゃん語に対応づける**（人間監督の指示：具体と
抽象の関係にある言葉は全て抽象側の赤ちゃん語に変換する）。この方針で
「動物」を21語から174語（犬種・猫種・魚種・鳥類等を含む）、「乗り物」を
20語から37語（車のボディタイプ・緊急車両の種類等を含む）まで拡充した。
新しい赤ちゃん語は作らず、既存の値（例：「馬」なら「んま」「おんま」
「ぱかぱか」）へ大人の言葉（キー）だけを増やしている。

多義語には注意する。「駒」は「馬」の意味（子馬・若い馬）と将棋の駒の
意味を持つが、日常語としては「駒が足りない」のような比喩表現で使われる
頻度が高く、動物の「馬」の意味で単独使用されることは稀なため、辞書には
追加していない（誤って将棋・人員配置の話を「んま」に変換してしまうリスクを
避けるため）。「春駒」（若い馬を指す語で、将棋の駒の意味を持たない）は
追加している。

2026-08-27、動物・乗り物に続けて残りの全サブカテゴリへ同じ方針を展開した。

| サブカテゴリ | 拡充前 | 拡充後 |
|---|---|---|
| 家族 | 6語 | 26語（「ママ」「お母さん」「母」等の呼び方バリエーション） |
| 体の部位 | 8語 | 10語 |
| 食べ物・飲み物 | 134語 | 153語 |
| 食事の動作 | 4語 | 7語 |
| 生活動作 | 29語 | 36語 |
| 排泄・生理現象 | 7語 | 11語 |
| 場所・お風呂まわり | 4語 | 5語 |
| 遊び | 4語 | 5語 |
| `baby_engineer_words.json`全体 | 117語 | 132語 |

家族・体の部位・排泄・場所・遊びは、確立した幼児語表現がWeb検索で十分に
見つからず、当初の目標規模（各30〜80語程度）には届いていない。無理に
増やさず、実在確認できた範囲にとどめている。

**既知の副作用**：「歯」（体の部位、1文字）のような短いキーと、新しく
追加した複合動詞キー（「歯磨きする」）が組み合わさると、動詞の活用形
（「歯磨きして」）が基本形（「歯磨きする」）と一致しないため、「歯」の
部分だけが浮いてマッチしてしまうことがある（`歯磨きして` →
`はぁは磨きして`）。動詞の活用非対応（6.4章）という既存の制限の一種として
扱い、深刻な誤変換ではないため個別の対処はしていない。

#### 6.4.1 部品分解による複合語対応（2026-08-27追加）

(a)(b)の辞書は「複合語を丸ごと1つのキーとして登録する」方式である
（例：`"仕様書": ["おやくそくのかみ"]`）。これだと、辞書に登録していない
似た構造の新しい複合語（例：「規約書」）には対応できない。

人間監督の指摘：「仕様書」を1語で覚えるのではなく、「仕様」（→「おやくそく」）
と「書」（→「かみ」）のように**部品ごとに列挙**すれば、似た構造の複合語にも
自動的に対応できる。この指摘を受け、分解しても安全な語だけを部品辞書
（`ai/dictionaries/baby_engineer_word_parts.json`）へ切り出した。

**なぜ文字列の最長一致だけでは危険か**：「書」を1文字のキーとして
`replace_longest_match()`に渡すと、動詞「書く」の活用形（「書いた」の
「書い」等）にも文字が重なるため、うまく除外できない。ここでは
**形態素解析でトークン化し、品詞が「名詞」または「接尾辞」のトークンだけ**
を対象にする`ai/src/fallback/token_match.py`の`replace_by_token()`を使う。
fugashi（unidic-lite）で確認したところ、「仕様書」は「仕様」（名詞）＋「書」
（接尾辞）の2トークンに分かれる一方、「書いた」は「書い」（動詞）＋「た」
（助動詞）に分かれ、「書」という1文字だけの独立トークンにはならない。
品詞込みでトークンの表層形を辞書と完全一致させることで、動詞「書く」との
衝突を避けている。

```json
// ai/dictionaries/baby_engineer_word_parts.json
{ "仕様": ["おやくそく"], "フロー": ["おやくそく"], "書": ["のかみ"], "図": ["のかみ"] }
```

「仕様書」→「仕様」＋「書」→「おやくそく」＋「のかみ」＝「おやくそくのかみ」。
辞書に無い「仕様概要図」も「仕様」＋「概要」（辞書に無いのでそのまま）＋
「図」で「おやくそく概要のかみ」のように自動的に変換される。

**部品化してよい語の条件**：`baby_fallback.py`は(a)(b)の複合語辞書を
`replace_by_token()`より**先**に処理する（理由は次の段落）。そのため、
部品辞書へ入れてよい語は次の両方を満たすものに限る。

1. 単語自体の変換結果が、(a)(b)の複合語辞書に登録済みの同じ語の変換結果と
   重複・矛盾しないこと（重複すると「規約書」が「おやくそくのかみのかみ」の
   ように二重変換される。このため「規約」は部品化せず(b)に残し、「規約書」
   という新語には対応していない）
2. (a)(b)のどのキーの一部としても出現しないこと（出現すると、その複合語が
   `replace_by_token()`より先に壊されてしまう）

**なぜ複合語辞書を先に処理するか**：「基本設計書」は語根「設計」が
『開発フロー』カテゴリの複合語（「外部設計」等）と衝突するため、部品化せず
(b)に複合語のまま残している。もし部品辞書を先に処理すると、「基本設計書」の
「書」が先に「のかみ」へ変換されてしまい、残った「基本設計」が「開発フロー」
カテゴリの複合語辞書とマッチしなくなる。逆に複合語辞書を先に処理すれば、
「基本設計書」（8文字）は部品辞書の「書」（1文字）より先に完全一致で
消費されるため、正しく守られる。

同様の理由で、(a)の日常語彙辞書に「手」（体の部位、1文字）があるため、
「手順」は部品化せず「手順書」のまま(b)に残している。(a)(b)は統合してから
一度に`replace_longest_match()`へ渡す（別々に呼ぶと、片方の短いキーが
もう片方の複合語の一部を先に食べてしまうため）。

**動詞の扱い（既知の制限）**：「食べる」「座る」のような動詞は、活用形
（食べた／食べます／食べて等）まで正確に変換しようとすると、動詞の活用型
（五段・一段・カ変・サ変）を判定する処理が必要になり複雑になる。今回は
辞書のキー（基本形の文字列）と**完全に一致した場合のみ**変換する割り切りに
した。「食べた」のような活用形は辞書にヒットせず、そのまま原文が残る
（10章「既知の制限」参照）。

**お母さん語**は、単語単位の置換辞書を持たない。人間監督の懸念（お母さんの文章に
絵文字や顔文字を必須にする採点基準は問題がある、Issue #15/#21）を踏まえ、
文体変換（6.7章）だけで表現する。

### 6.5 文末表現の変換（赤ちゃん語）

```python
ENDING_RULES: list[tuple[re.Pattern, str]] = [
    (re.compile(r"でした[。\.]?$"), "だったのー。"),
    (re.compile(r"ました[。\.]?$"), "たのー。"),
    (re.compile(r"します[。\.]?$"), "するのー。"),
    (re.compile(r"です[。\.]?$"), "でちゅ。"),
    (re.compile(r"ます[。\.]?$"), "まちゅ。"),
    (re.compile(r"だ[。\.]?$"), "なの。"),
]
```

文末に一致するルールが無い場合（体言止め、口語調など）は、末尾に「でちゅ」を
補う。感嘆詞（「ばぶー」「おぎゃー」）は文頭に1つだけ、文の内容が「疲れた」
「つらい」系のときに付ける（6.6章の気持ちワード検出と連動）。

### 6.6 気持ちワードと一般規則

- 「疲れた」「つらい」「無理」「大変」「難しい」「眠い」を含む文には、内容語の
  変換に加えて文頭へ「ばぶー」「おぎゃー」のいずれかを付ける（固定の対応表、
  ランダム選択はしない。同じ入力に対して常に同じ出力になるようにするため）。
- 一人称（「私」「僕」「俺」）は「ぼく」「わたち」に置換する（baby のみ）。
- 辞書に無い名詞・動詞は原形のまま残す。無理に全文をひらがな化すると、技術用語
  （React.js、index.ts等）まで壊れるため、辞書に載っている語だけを対象にする。

### 6.7 お母さん語のフォールバック

`ai/transform_api.py`の`INSTRUCTIONS["mother"]`（Geminiプロンプト）が定義している
「言い換えのしかた」を、ルールベースでも同じ方向性で再現する。

```python
MOTHER_ENDING_RULES: list[tuple[re.Pattern, str]] = [
    (re.compile(r"しろ[。\.]?$"), "してもらえるかな。"),
    (re.compile(r"して[。\.]?$"), "してもらえるかな。"),
    (re.compile(r"だ[。\.]?$"), "だね。"),
    (re.compile(r"です[。\.]?$"), "なんだね。"),
    (re.compile(r"ます[。\.]?$"), "るのね。"),
]
```

さらに文全体の前後に労いのフレーズを添える（5章のNGワード置換で穏当化された
文章に対して行うため、二重の緩和になる）。

```python
MOTHER_PREFIXES = ["そうだったのね、", "よしよし、", "だいじょうぶだよ、"]
MOTHER_SUFFIXES = ["よく頑張ったね。", "無理しないでね。", "えらいよ。"]
```

前後のフレーズは、文章のハッシュ値ではなく**文字数**から機械的に選ぶ
（外部の乱数に依存させず、同じ入力なら常に同じ出力にする）。絵文字・顔文字は
付けない。「お母さんの文章に絵文字を必須にする採点基準は問題」という人間監督の
判断（1.2章）と同じ理由で、機械的に固定の顔文字を混ぜるのも避ける。

### 6.8 幼児語訛り（舌足らず）の音韻変換（2026-08-27追加、赤ちゃん語のみ）

人間監督の指定した4つの規則を、`ai/src/fallback/toddler_accent.py`の
`apply_toddler_accent()`で実装している。お母さん語には適用しない
（お母さんが舌足らずに話すのは不自然なため）。

| # | 規則 | 例（ローマ字） | 例（ひらがな） |
|---|---|---|---|
| 1 | た行の直後のさ行が、同じ段のた行に変わる | watasi → watati | わたし → わたち |
| 2 | 単語の先頭のか行が、同じ段のた行に変わる | kinou → tinou | きのう → ちのう |
| 3 | わ・を の子音が抜け落ちて母音だけになる | watasi → atasi | わ → あ |
| 4 | 「さ」が「しゃ」に変わる | usagisan → usagisyan | さ → しゃ |

適用順序は**2 → 1 → 3 → 4**（`to_baby_words()`内では語尾変換の直後）。
規則2だけは形態素解析で単語の先頭を判定する必要があるため、他の規則で
文字列を変形する前に行う。カタカナ・漢字・英数字はどの規則にも一致しない
ため素通りする（結果的に、外来語の辞書キー「セダン」「カレー」等を壊さない）。

**処理順序の制約（回帰テストあり）**：

- **語尾変換 → 訛り変換の順で行う。** 逆順にすると、「してください」が
  訛り変換で「してつだしゃい」のようになり、語尾変換の正規表現パターン
  （`してください$`）と一致しなくなる。語尾変換後の全パターン（「でちゅ。」
  「してほしいのー。」等）が訛り変換の対象になる音を含まないことは確認済み。
- **訛り変換 → 辞書変換の順で行う**（6.4章の処理は6.8の後）。人間監督の
  指定どおり、辞書変換の前に文全体へ適用する。

**既存の辞書キーへの影響**：訛り変換を辞書変換より前に適用するため、
「うさぎ」→「うしゃぎ」のように、辞書のキー自体が訛って一致しなくなる
ことがある。`dictionary_loader.load_variant_dictionary()`が、各キーに
`apply_toddler_accent()`を適用した結果が元のキーと異なる場合、その訛った
形を同じ値で自動的に別名登録する（辞書ファイル自体を手で書き換える必要は
無い）。影響を受けることを確認したキー（一部）：「うさぎ」→「うしゃぎ」、
「かぼちゃ」→「たぼちゃ」、「きゅうり」→「ちゅうり」、「くしゃみ」→
「つちゃみ」、「かくれんぼ」→「たくれんぼ」、「さくらんぼ」→「しゃくらんぼ」、
「さつまいも」→「しゃつまいも」、「から揚げ」→「たら揚げ」。

## 7. モデレーションとの関係

3章のとおり、変換前・変換後の両方で`ai/moderation_rules.py`の`check_rules()`を
呼ぶ（design_doc.md FR-MOD-001〜002）。フォールバック経路でも同様に事後
モデレーションを行う。**フォールバック生成が辞書変換であっても、事後検査は省略しない**
（辞書変換の結果が偶然NG語と一致する可能性を排除できないため）。

## 9. テスト方針

- `replace_longest_match()`の単体テスト：複合語の最長一致、辞書に無い語の非変換
- 赤ちゃん語・お母さん語それぞれのフォールバック生成：入力→期待する出力の対応表
- `transform()`全体：Gemini呼び出しをモックし、(1)成功時にGemini経路が使われる、
  (2)タイムアウト時にフォールバックへ切り替わる、(3)事前/事後モデレーションで
  blockされたら`transformedText`が`null`になる、の3点を確認する
- NGワード置換：置換対象語が変換前に消えていることを確認する回帰テスト

## 10. 既知の制限

- フォールバック生成は「文体として本当に赤ちゃん語らしいか」を判定しない
  （1.2章）。辞書と規則で機械的に言い換えるだけであり、Geminiほど自然な文章には
  ならない。
- 辞書は初期セットのみで、全網羅ではない。辞書に無い語はそのまま残る。
- 複合語の最長一致は、辞書に登録した語しか結合できない。形態素解析による
  一般的な複合語推定（未知の複合語を自動で見つける）は行わない。
- 動詞（「食べる」「座る」等）は辞書のキー（基本形の文字列）と完全一致した
  場合のみ変換する。「食べた」「食べます」のような活用形には対応しない
  （6.4章）。

## 1. 目的・スコープ・非スコープ

### 1.1 目的

Deno公開API、Python推論サービス、フロントエンドの3者が同じ契約を読み、実装と統合に進むための詳細仕様を定義する。

**完了条件：** フロント担当が読んで API 呼び出しをモック実装でき、Deno 担当が AI サービスとの連携ロジックを実装でき、Python 担当が入出力契約を実装できる状態。

### 1.2 スコープ（対象）

以下の2エンドポイントと責務境界：

- **`POST /api/ai/evaluate`** … 文章の「赤ちゃん度／お母さん度」を年齢値で評価する
- **`POST /api/ai/transform`** … 文章を赤ちゃん言葉・お母さん言葉に変換し、モデレーション結果を返す
- **責務境界** … 判定ロジックの所在（Python）、強制と再検査の所在（Deno）、両者の間で渡さない情報

入力制約、エラー処理、認証境界、タイムアウト、ログ・プライバシー方針、フロント側の画面分岐も含む。

### 1.3 非スコープ（対象外）

- 投稿・コメント・プロフィール等、AI以外のすべてのAPI詳細
- モデル学習コード（学習済みモデルの推論のみが対象）
- 学習データ生成手順の詳細
- UIデザイン
- 実装コード（インターフェース定義のみ）
- NG辞書そのものの語彙一覧（別管理。本書では所在と参照方法のみ定義）

## 2. システム境界

```
Frontend
  |
  |  HTTP（利用者セッション）
  v
Deno Public API
  - 利用者認証
  - 入力検証・サイズ制限・列挙値検証
  - レート制限・タイムアウト
  - Python のモデレーション判定を「呼び出して強制する」
  - 上流エラーを利用者向けエラーへ変換
  - requestId 発行とログ記録
  |
  |  HTTPS（サービス間認証。利用者トークンは転送しない）
  v
Python / Hugging Face
  - 文章評価（scikit-learn）
  - 文章変換（ルールベース）
  - モデレーション判定（NG辞書・正規化ルールの唯一の所在）
```

**重要な原則：**

- フロントは Hugging Face を直接呼ばない。必ず Deno を経由する
- **NG辞書と正規化ルールは Python 側にのみ置く。Deno 側に同等の判定ロジックを再実装しない**（詳細は 6 章）
- Deno は利用者認証、入力上限、レート制限、タイムアウト、保存時の強制を担当する
- Python は DB を持たず、利用者情報を扱わない
- Python は `accountId`、`personaId`、利用者トークン、DBキー、セッションCookieを受け取らない
- Deno → Python はサービス間認証を用いる（方式は **[TBD-5]**）

## 4. `POST /api/ai/evaluate`

### 4.1 目的と責務の限定

投稿・コメントの文章から「何歳児相当か」を年齢値で評価する。プロフィール画面のステータス表示や、タイムラインのレコメンド用類似度に使う。

**`evaluate` が担当しないこと（重要）：**

- 文章の変換（書き換え）を行わない
- モデレーション判定（`allow` / `block`）を返さない
- 投稿可否・保存可否を判定しない
- 投稿・コメントの保存を行わない

上記はすべて `transform` と保存時処理（6 章）の責務である。`evaluate` の戻り値を投稿可否の判断に使ってはならない。

### 4.2 評価軸（`baby` と `mother` は基準が異なる）

| `personaType` | 何を測るか | 主な着眼点 | 戻り値の読み方 |
|---|---|---|---|
| `baby` | **文章自体の幼さ** | 幼児語、語彙の少なさ、文の短さ、文法の崩れ、感情の直接性 | 「この文章は何歳児相当の幼さか」 |
| `mother` | **何歳児向けのよしよしか** | 労い・受容の強さ、噛み砕きの度合い、相手に期待する理解度 | 「この文章は何歳児に向けたあやしか」 |

**同じ文章を `baby` と `mother` で評価しても、測っている対象が違うため値は一致しない。** 両者の値を直接比較したり、同一の尺度として平均を取ったりしてはならない。

### 4.3 リクエスト仕様

| フィールド | 型 | 必須 | 制約 |
|---|---|---|---|
| `body` | string | 必須 | 1文字以上。空文字列・空白のみは不可。上限は 7 章 |
| `personaType` | string | 必須 | `"baby"` または `"mother"` のみ |

```json
{
  "body": "あああ今日つかれた。ねむい。",
  "personaType": "baby"
}
```

### 4.4 レスポンス仕様

```json
{
  "estimatedAge": 2.0
}
```

| フィールド | 型 | 説明 |
|---|---|---|
| `estimatedAge` | number | 推定年齢値。範囲・刻みは **[TBD-1]**。`baby` では文章自体の幼さ、`mother` では対象年齢を表す |

**`confidence`（確信度）について：**

- `confidence` を返すかどうかは **[TBD-7]** で未決定。**現時点の契約には含めない**
- 返す場合も、モデル出力の生値（未校正のスコア）をそのまま返してはならない。校正済みの値のみを返す
- 未校正値をそのまま出すと、フロントが「70%だから信頼できる」と誤読する。校正が済むまでは返さない方針を既定とする

### 4.5 成功例

#### 例1：`baby`（文章自体の幼さを測る）

リクエスト:

```json
{
  "body": "あああ今日つかれた。ねむい。",
  "personaType": "baby"
}
```

レスポンス（200）:

```json
{
  "estimatedAge": 2.0
}
```

#### 例2：`mother`（何歳児向けのあやしかを測る）

リクエスト:

```json
{
  "body": "今日もよくがんばったねえ。えらいえらい。ゆっくり休もうね。",
  "personaType": "mother"
}
```

レスポンス（200）:

```json
{
  "estimatedAge": 3.5
}
```

同じ `3.5` でも、例1の系列（幼さ）と例2の系列（対象年齢）は別の尺度である。

### 4.6 検証エラー例

#### 例3：`body` が空文字列

リクエスト:

```json
{
  "body": "",
  "personaType": "baby"
}
```

レスポンス（422）:

```json

```

#### 例4：`personaType` が列挙値外

リクエスト:

```json
{
  "body": "つかれた",
  "personaType": "father"
}
```

レスポンス（422）:

```json

    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
```

## 5. `POST /api/ai/transform`

### 5.1 目的

利用者が書いた文章を「赤ちゃん言葉」または「お母さん言葉」に変換する。変換結果はプレビューであり、保存はしない（F-4）。

### 5.2 リクエスト仕様

| フィールド | 型 | 必須 | 制約 |
|---|---|---|---|
| `body` | string | 必須 | 1文字以上。上限は 7 章 |
| `style` | string | 必須 | `"baby"` または `"mother"` のみ |

```json
{
  "body": "今日のコードレビュー疲れた。複雑すぎて理解できない部分がある。",
  "style": "baby"
}
```

### 5.3 レスポンス仕様（採用済み契約）

```json
{
  "action": "allow",
  "transformedText": "きょうのこーどれびゅー、つかれちゃった。",
  "reasonCodes": []
}
```

| フィールド | 型 | 説明 |
|---|---|---|
| `action` | string | `"allow"` / `"rewrite_required"` / `"block"` の3値 |
| `transformedText` | string \| null | `allow` は変換結果、`rewrite_required` は優しい書き換え案、`block` は `null` |
| `reasonCodes` | string[] | 判定理由コードの配列。`allow` では空配列 |

**`action` の意味：**

- **`allow`** … そのまま利用してよい変換候補
- **`rewrite_required`** … 原文のままでは利用不可。書き換え案を提示し、利用者に確認・修正を促す
- **`block`** … 安全に提示できる変換がない。`transformedText` は `null`

内部思考、NG辞書の語彙、スタックトレースは返さない（F-10）。

### 5.4 成功例

#### 例5：`allow`

リクエスト:

```json
{
  "body": "今日のコードレビュー疲れた。複雑すぎて理解できない部分がある。",
  "style": "baby"
}
```

レスポンス（200）:

```json
{
  "action": "allow",
  "transformedText": "きょうのこーどれびゅー、つかれちゃった。むずかしくてわかんない。",
  "reasonCodes": []
}
```

#### 例6：`rewrite_required`

リクエスト:

```json
{
  "body": "マネージャーが無能すぎて本当にむかつく。",
  "style": "mother"
}
```

レスポンス（200）:

```json
{
  "action": "rewrite_required",
  "transformedText": "お仕事、大変だったんだねえ。うまくいかないことがあると疲れちゃうね。ゆっくり休もうね。",
  "reasonCodes": ["harsh_language_toward_others"]
}
```

#### 例7：`block`

リクエスト:

```json
{
  "body": "〇〇社の××という人間は死ね。",
  "style": "baby"
}
```

レスポンス（200）:

```json
{
  "action": "block",
  "transformedText": null,
  "reasonCodes": ["specific_threat", "hate_speech"]
}
```

`block` でも HTTP は 200 である（業務結果であり通信エラーではない。8 章参照）。

### 5.5 `reasonCodes` のコード例

> **注意：以下はコード例（仮）であり、正式な API 契約ではない。** 正式一覧・命名規則・粒度は **[TBD-4]** で決定する。フロント・Deno は本節の文字列をハードコードせず、`reasonCodes` は「未知のコードが来ても壊れない配列」として扱うこと。表示文言との対応表は正式一覧の確定後に別途定義する。

| コード例（仮） | 想定する意味 | 主に返る `action` |
|---|---|---|
| `harsh_language_toward_others`（仮） | 他者への攻撃的表現 | `rewrite_required` |
| `specific_threat`（仮） | 特定個人・団体への脅迫 | `block` |
| `self_harm_hint`（仮） | 自傷の示唆 | **[TBD-9]** |
| `violence_hint`（仮） | 暴力の示唆 | `rewrite_required` / `block` |
| `hate_speech`（仮） | 差別・ヘイト表現 | `block` |
| `personal_data`（仮） | 個人情報の露出 | `rewrite_required` / `block` |

## 6. モデレーションの責務と処理フロー

### 6.1 責務の原則（二重管理を避ける）

**NG辞書・正規化ルール・モデレーション判定は Python 側にのみ実装する（F-6）。** Deno 側に同等の判定ロジックを再実装すると、辞書更新のたびに2箇所を直す必要が生じ、片方だけ古くなった時点で「Deno は通すが Python は弾く」という判定ずれが起きる。

したがって役割は次のように分ける。

| 役割 | 担当 | 内容 |
|---|---|---|
| **判定ロジックの実装** | Python のみ | NG辞書、正規化ルール、文脈判定、`action` と `reasonCodes` の決定 |
| **判定の強制** | Deno | 保存前に Python の判定を呼び出し、`block` なら保存を拒否する |
| **構造の検証** | Deno | JSON形式、型、列挙値、サイズ上限（判定ロジックではない） |

Deno が独自に持つのは「構造の検証」と「強制」だけであり、**NG語の判断は行わない**。

### 6.2 `transform` 呼び出し時のフロー

```
[Deno]
 1. 利用者認証
 2. JSON形式・型・列挙値・サイズ上限を検証（不備は 422）
 3. レート制限を確認（超過は 429）
 4. Python へ body と style のみを転送（利用者情報は送らない）

[Python]
 5. 表示用の原文を保持したまま、検査用文字列を正規化
 6. 変換前のモデレーション判定（共通NG・文脈）
 7. style=mother では「マサカリ表現」も判定
 8. 変換前判定で確定した場合は、変換せず block / rewrite_required を返す
 9. 文章変換を実行
10. 変換結果を再正規化し、変換後のモデレーション判定（F-7）
11. action / transformedText / reasonCodes を返す

[Deno]
12. レスポンスの型・サイズを検証（不正なら 502）
13. そのまま利用者へ返す（保存はしない。F-4）
```

### 6.3 保存時のフロー（改ざん対策）

```
[Frontend]
 1. 利用者が最終テキストを確認し、保存を要求

[Deno]
 2. フロントから来た AI結果（action など）は信用しない（F-9）
 3. 保存対象の最終テキストで Python のモデレーション判定を「もう一度」呼び出す
    - Deno 側で独自判定はしない。同じ Python 判定を再利用する
 4. 判定が block → 保存せずエラーを返す
 5. 判定が allow / rewrite_required → 150文字制限（F-5）等を検証して保存
```

「前後2回」という表現は、**`transform` 内部での変換前後2回（F-7）** と、**保存時の再判定（F-9）** の2つを指す。いずれも判定の実体は Python 側の同一ロジックであり、Deno が別の辞書で判定するわけではない。

## 7. 入力制約

| 項目 | 制約 | 備考 |
|---|---|---|
| `body` 最小長 | 1文字以上（空文字列・空白のみは不可） | 空文字列は 422 |
| `body` 最大長（`transform`） | **[TBD-2]**（提案：1000文字） | 上限超過は 422 |
| `body` 最大長（`evaluate`） | **[TBD-2]**（提案：1000文字） | 同上 |
| 保存される本文 | 150文字以内（F-5） | 保存時に Deno が検証 |
| 文字数カウント規則 | **[TBD-8]** | 絵文字・結合文字・改行・サロゲートペアの数え方が未定義 |
| `personaType` / `style` | `"baby"` または `"mother"` のみ | 列挙値外は 422 |
| Content-Type | `application/json` | 不一致は 400 |
| 制御文字 | 改行・タブ以外の制御文字は拒否 | 正規化は Python 側 |

**注意：** 文字数カウント規則（**[TBD-8]**）が未定のため、上限値だけを先に実装すると Deno と Python で数え方が食い違う。上限の実装は TBD-8 の確定後に行う。

## 8. 業務結果とHTTPエラー

### 8.1 業務結果は 200 で返す

`block` や `rewrite_required` は**正常に判定が完了した業務結果**であり、HTTP 200 で返す。HTTPエラーコードには使わない。

| 業務結果 | HTTP | 意味 |
|---|---|---|
| `allow` | 200 | 変換候補を提示できる |
| `rewrite_required` | 200 | 書き換え案を提示する |
| `block` | 200 | 安全な変換を提示できない |

### 8.2 HTTPエラー

| コード | 使用条件 | 再試行 |
|---|---|---|
| 400 | JSON として解析できない、Content-Type 不正 | 不可（修正が必要） |
| 401 | 未認証・トークン無効 | 不可 |
| 403 | 認証済みだが権限なし | 不可 |
| 422 | JSON は正しいが値が不正（空文字列、列挙値外、上限超過） | 不可 |
| 429 | レート制限超過 | 可（`Retry-After` 尊重） |
| 500 | Deno 内部エラー | 可 |
| 502 | Python からの応答が不正・Python 側エラー | 可 |
| 503 | Python / Hugging Face が停止中または起動中 | 可 |
| 504 | Python への呼び出しがタイムアウト | 可 |

**[TBD-11]** 400 と 422 を分けるか、400 に統合するかは未決定。上表は分ける前提で記載している。

### 8.3 共通エラーレスポンス

すべてのエラーは同じ形で返す。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "fields": [
      { "field": "body", "code": "too_long" }
    ]
  },
  "requestId": "01J9Z8M4Q7YQ2K3W5V6X7Y8Z9C"
}
```

| フィールド | 型 | 説明 |
|---|---|---|
| `error.code` | string | 機械判定用の固定コード。UPPER_SNAKE_CASE |
| `error.message` | string | 利用者向けの日本語文。内部情報を含めない |
| `error.fields` | array \| 省略 | 検証エラー時のみ。どのフィールドがなぜ不正か |
| `requestId` | string | 本リクエストの識別子 |

`error.code` の値（例）：`BAD_REQUEST`、`UNAUTHORIZED`、`FORBIDDEN`、`VALIDATION_ERROR`、`RATE_LIMITED`、`UPSTREAM_ERROR`、`UPSTREAM_UNAVAILABLE`、`UPSTREAM_TIMEOUT`、`INTERNAL_ERROR`。正式一覧は **[TBD-4]** と併せて確定する。

### 8.4 `requestId`

- Deno がリクエスト受信時に発行し、**すべての**レスポンス（成功・失敗とも）に含める
- ヘッダー `X-Request-Id` とレスポンス本文の両方に載せる
- Deno → Python 呼び出しにも同じ値を伝播し、両者のログを突き合わせられるようにする
- 利用者からの問い合わせは `requestId` で追跡する。本文の内容を聞き取る必要をなくす
- 形式：**[TBD]** ULID を提案（時系列ソート可能）

## 9. 認証・セキュリティ境界

### 9.1 Frontend → Deno

- 利用者セッションによる認証。未認証は 401
- レート制限は利用者単位（閾値は **[TBD]**）

### 9.2 Deno → Python

- **サービス間認証を必須とする。方式は [TBD-5]**（共有シークレットヘッダー / Hugging Face トークン / 相互TLS のいずれか）
- Python エンドポイントを公開ネットワークに素で晒さない
- **転送してよいもの：** `body`、`style` / `personaType`、`requestId`
- **転送してはならないもの：** `accountId`、`personaId`、利用者トークン、セッションCookie、DBキー、メールアドレス、その他の利用者識別子（F-3）
- Python は受け取っていない情報をログに書けないため、この境界が最大のプライバシー防護になる

### 9.3 レスポンスに含めないもの

内部思考、NG辞書の語彙、判定閾値、モデル内部スコア、スタックトレース、上流のエラーメッセージ原文（F-10）。上流エラーは Deno で 502 / 503 / 504 に変換して返す。

## 10. タイムアウトと停止時の扱い

| 項目 | 内容 |
|---|---|
| Deno → Python タイムアウト | **[TBD]**（提案：接続 3 秒 / 全体 10 秒） |
| Hugging Face のコールドスタート | Space がスリープしている場合、初回応答に数十秒かかり得る |
| スリープ中の応答 | Deno は 503 を返し、フロントは「AIの準備中です。少し待ってからもう一度お試しください」と表示する |
| 再試行 | Deno 側での自動リトライは 1 回まで（**[TBD]**）。多重リトライでコールドスタートを悪化させない |
| フォールバック方針 | **[TBD-6]**（提案：fail-closed。AI変換機能を一時的に使用不可にし、通常投稿は継続可能とする） |
| fail-open を採らない理由 | 判定不能時に変換結果を通すと、NG内容が素通りする |

**保存時の判定（6.3）で Python に到達できない場合の扱いは [TBD-6] に含める。** 「判定できないから保存を通す」は選択しない前提で提案している。

## 12. フロント担当向けの利用フロー

### 12.1 `evaluate` の使い方

```
1. 投稿・コメントの表示、またはプロフィール更新のタイミングで呼ぶ
2. body と personaType を送る
3. estimatedAge を表示用に使う
4. 422 が返ったら入力を見直す（空文字列など）
5. 503 / 504 が返ったら年齢表示を「—」等にして、投稿機能自体は止めない
```

`evaluate` の結果で投稿ボタンを無効化してはならない（4.1）。

### 12.2 `transform` の使い方

```
1. 利用者が「赤ちゃん語に変換」ボタンを押す
2. POST /api/ai/transform に body と style を送る
3. ローディング表示を出す（コールドスタート時は数十秒かかり得る）
4. action で分岐する

   allow
     - transformedText をプレビュー表示
     - 「この文で投稿」「自分で直す」を選べるようにする

   rewrite_required
     - transformedText を「やさしい言い方の候補」として表示
     - 元の文のままでは投稿できないことを伝える
     - 利用者が編集してから再度変換できるようにする

   block
     - 変換候補は表示しない（transformedText は null）
     - 「この内容は変換できません」と伝える
     - reasonCodes をそのまま画面に出さない（内部コードのため）

5. 利用者が投稿を確定したら、投稿APIへ最終テキストを送る
6. 投稿APIは保存前に再判定する（6.3）。ここで拒否される場合もあるため、
   保存エラーのハンドリングを用意する
```

**注意：** `transform` の戻り値をそのまま投稿APIへ「検査済み」として渡しても、保存時に再判定される（F-9）。フロント側で判定結果をキャッシュして検査を省略させることはできない。
